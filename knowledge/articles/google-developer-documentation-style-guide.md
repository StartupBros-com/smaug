Google’s public editorial guide for developer-facing docs, recommended as a Claude/ChatGPT skill to kill “Claude-lish” and “Chat-lish.” Nate Jones found it clearer than an ASD-STE100 Simplified Technical English skill: conversational but not cute, second person, active voice, conditions before instructions, sentence-case headings, serial commas, code font for code, bold for UI, unambiguous dates, descriptive link text, and alt text on images. The landing page is the index; [Highlights](https://developers.google.com/style/highlights), [Voice and tone](https://developers.google.com/style/tone), [Text-formatting summary](https://developers.google.com/style/text-formatting), and the [word list](https://developers.google.com/style/word-list) are the pages worth stuffing into a skill.

Reference hierarchy: project-specific style first, then this guide, then Merriam-Webster (spelling), Chicago 17th (nontechnical), and the Microsoft Writing Style Guide (technical, with the caveat that some of it is Microsoft-product-specific). Android and Google Cloud callouts are marked in-page. Orwell’s rule is official: break any guideline sooner than write something barbarous, but stay consistent once you depart. Last updated 2026-04-27 on the about page.

## Key Takeaways

- Best used as a compact skill, not a read-through: Highlights + word list cover most model-prose failures
- Second person + active voice + condition-before-instruction is the anti-slop core
- Do not pre-announce features in docs; write for a global and accessible audience
- Hierarchy is project style → this guide → MW / Chicago / Microsoft — not the other way around
- Guidelines, not rules; consistency after a deliberate exception matters more than compliance
